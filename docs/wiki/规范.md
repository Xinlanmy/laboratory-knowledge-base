# 实验室技术知识库文档写入规范

> 这是实验室提供的内容规范。它指导部门仓库如何维护正文；本总目录仓库只存放此规范和链接，不存放章节正文。

## 一、建设目标

实验室知识库不是简单的资料存储空间，而是面向实验室长期发展的可持续更新技术知识体系。

知识库应逐步形成：

> **基础知识 → 技术模块 → 实践项目 → 完整项目 → 经验复盘 → 下一阶段迭代**

每一代成员都应在前一代的基础上继续学习、实践、补充和修正，使知识库持续成长。

最终目标是：

> **新成员可以通过知识库学习基础知识；有基础的成员可以依据项目文档复现已有项目；后续成员可以在已有成果基础上继续开发。**

## 二、总体内容架构

实验室知识库按照以下内容逻辑组织：

```text
实验室知识体系
├── 基础知识
├── 技术模块
├── 学习课程
├── 项目实践
├── 技术经验
└── 历史与交接
```

### 基础知识

回答“这个领域需要知道什么”，例如 Python、Linux、C/C++、数学、Git 和 ROS 基础。

### 技术模块

回答“这个技术具体怎么理解和使用”，例如 ROS 2 节点通信、YOLO 目标检测、机械臂运动学、机器狗 SDK、Jetson 模型部署、MCU 通信和 SLAM。技术模块应尽量独立、可学习、可复用。

### 学习课程

回答“新成员应该按照什么顺序学习”。课程应围绕“入门 → 基础 → 实践 → 项目”建立学习路径。

### 项目实践

回答“学完之后如何真正做出来”。项目文档应包含足够信息，使其他成员可以依据文档完成复现。

### 技术经验

回答“以前的人踩过什么坑”，记录开发过程中产生的、具有复用价值的问题与解决方案。

### 历史与交接

回答“以前做过什么、现在做到哪里、未来可以做什么”。

## 三、项目文档写入规范

### 1. 每个项目必须建立 README

所有具有实际开发价值的项目都必须有独立的 `README.md`。README 是项目的技术说明与复现入口，不只是项目简介。

目标是：

> **一个具备相应基础的实验室成员，仅根据 README 和项目资料，就能够理解项目并完成复现。**

### 2. 项目 README 信息架构

项目 README 原则上按照以下顺序组织。与项目无关的部分可以注明“不适用”，但不能省略关键的复现信息。

#### ① 项目概述

说明项目是什么、为什么开展、解决什么问题，以及最终实现了什么。

#### ② 项目目标

明确项目希望达到的技术目标和最终成果。目标应具体、可理解，尽量说明使用什么方法实现什么功能。

#### ③ 技术路线

说明项目的技术架构以及数据流或控制流程，使后来者能够快速理解项目如何工作。例如：

```text
传感器 → 数据采集 → 感知算法 → 决策 → 控制 → 机器人执行
```

#### ④ 开发环境

记录实际运行所依赖的环境，包括适用的操作系统、Python/C++ 版本、ROS/ROS 2 版本、CUDA 版本、深度学习框架、主要依赖、开发工具及其他关键环境。应记录真正影响复现的信息，不能只写“安装依赖即可运行”。

#### ⑤ 硬件环境

涉及硬件的项目必须记录设备名称与型号、核心参数、设备连接关系、关键接口、必要配件和使用注意事项，使后来者能够判断复现项目需要哪些硬件。

#### ⑥ 核心代码

说明核心代码的位置、各模块的职责、模块之间的协作关系，以及项目中应优先阅读的关键部分。不要求 README 逐行解释全部代码，但应帮助后来者找到入口。

#### ⑦ 项目实现

按照实际开发顺序说明实现过程，例如：

```text
环境配置 → 硬件连接 → 数据采集 → 算法部署 → 机器人控制 → 系统联调 → 最终运行
```

#### ⑧ 复现步骤

这是项目 README 的核心部分。复现步骤应尽可能做到按照文档一步一步操作即可完成项目复现，并明确：

1. 需要准备什么；
2. 需要安装什么；
3. 需要进行哪些配置；
4. 需要运行哪些命令或程序；
5. 预期出现什么结果；
6. 如何判断运行成功。

容易出错或具有特殊要求的步骤，应单独说明。

#### ⑨ 项目成果

记录实现的功能、实验结果、Demo、视频、图片、性能指标、比赛成绩或其他成果。描述应尽可能基于可验证的结果，而不是只写主观评价。

#### ⑩ 已知问题

如实记录尚未解决的问题、技术限制、稳定性问题、性能瓶颈、硬件限制和环境兼容问题，不应为了让项目看起来完整而隐藏问题。

#### ⑪ 后续方向

说明下一代成员可以从哪里继续，包括可优化内容、可增加的功能、当前技术瓶颈、值得研究的方向和下一阶段建议。

## 四、课程文档写入规范

实验室课程是知识库中的学习路径，不是简单的资料合集。每门课程应说明以下内容：

### ① 课程定位

说明课程解决什么问题，以及它在部门学习体系中的位置。

### ② 面向对象

说明适合什么基础的成员，例如零基础、有 Python 基础或有 ROS 基础的成员。

### ③ 前置知识

列出学习本课程之前需要掌握的知识或技能。

### ④ 学习目标

说明完成课程后，成员应该掌握哪些知识、能够完成哪些任务。

### ⑤ 知识模块

按照学习逻辑组织课程内容，通常包括：

```text
基础概念 → 核心原理 → 基本操作 → 实践 → 综合应用
```

### ⑥ 实践内容

尽量提供可以实际运行、操作或验证的实验与练习，并说明预期结果。

### ⑦ 项目衔接

说明学完课程后可以进入哪些实践或项目，形成“课程 → 能力 → 项目”的衔接关系。

## 五、技术模块文档写入规范

技术模块是知识库中可反复学习和复用的知识单元，例如 ROS 2 通信、YOLO 部署、Jetson 环境配置、机械臂运动学或 MCU 串口通信。每个模块应尽量说明：

1. **技术是什么：**基本概念和作用；
2. **为什么使用：**它解决什么问题；
3. **工作原理：**理解和使用它所需的核心机制；
4. **使用环境：**依赖的软硬件及版本要求；
5. **基本使用：**最小可运行示例或基本操作；
6. **实际应用：**它在实验室项目中的使用方式；
7. **常见问题：**实际遇到的问题及解决办法；
8. **延伸方向：**学完后可以继续学习的内容。

技术模块应能够独立成为可学习、可复用的知识单元。

## 六、技术问题与踩坑文档规范

具有复用价值的技术问题应按照以下信息架构记录：

> **现象 → 环境 → 原因 → 解决方案 → 验证 → 经验**

文档应说明问题表现、发生时的软硬件环境、原因分析、采取的解决方案、验证结果，以及后续可以复用的经验。已经解决的问题应留下记录，避免下一届重复排查。

## 七、硬件资料写入规范

硬件资料不能只保留厂商说明书。对实验室实际使用过的硬件，应逐步形成自己的使用知识，重点记录：

- 设备名称、型号和主要用途；
- 核心参数与接口；
- 使用环境及配套软件或 SDK；
- 基本使用方法；
- 与其他设备的连接关系；
- 实际项目应用；
- 使用注意事项与常见问题。

目标是让新成员知道设备是什么、如何使用，以及它曾应用于哪些项目。

## 八、项目复盘规范

项目结束后应留下复盘信息，重点回答：

### 做对了什么？

记录有效的技术方案和实践方法。

### 做错了什么？

记录未奏效或造成额外成本的方案。

### 为什么失败？

记录真实原因和必要证据。

### 哪些经验值得保留？

提炼能够迁移到其他项目的知识。

### 下一次应该怎么做？

提出可以执行的改进方案。

项目复盘用于提高下一代项目的起点，不用于评价成员个人。

## 九、知识库更新规范

知识库是持续更新的电子书，不是一次性完成的文档。新增知识、补充现有内容、修正错误、更新项目和沉淀经验，都是正常维护的一部分。

发现已有内容存在错误、过时、不完整、难以理解或无法复现等情况时，应及时修正或补充，并尽量说明重要修改的原因及影响。

## 十、内容质量标准

进入知识库的核心内容应尽量满足以下标准：

### 1. 能理解

表达清楚，关键术语和背景足以让目标读者理解。

### 2. 能学习

内容有合理的顺序，成员可以据此掌握知识或技能。

### 3. 能复现

项目包含必要的环境、硬件、配置和操作说明，读者能够按文档验证结果。

### 4. 能延续

后续成员能够理解现有成果、已知问题和下一步方向，并在此基础上继续开发。

知识库追求的是“有效知识最多”，而不是“资料最多”。

## 十一、不同类型内容的核心目标

| 内容类型 | 核心问题 |
|---|---|
| 基础知识 | 我需要知道什么？ |
| 技术模块 | 这个技术怎么理解和使用？ |
| 课程 | 我应该按什么顺序学习？ |
| 项目 | 这个东西怎么做出来？ |
| 项目 README | 我如何理解并复现它？ |
| 技术经验 | 以前的人遇到过什么问题，如何解决？ |
| 项目复盘 | 下一次应该如何做得更好？ |
| 后续方向 | 下一代可以继续做什么？ |

## 十二、持续迭代目标

知识体系逐步形成以下循环：

```text
基础知识
    ↓
技术模块
    ↓
部门课程
    ↓
实践训练
    ↓
实验室项目
    ↓
项目复盘
    ↓
技术经验
    ↓
下一代成员继续学习与开发
    ↺
```

每一代成员都应做到：

> **学习已有知识 → 使用已有知识 → 产生新的知识 → 更新知识库 → 留给下一届。**

最终，实验室知识库将成为持续生长的技术电子书与项目技术档案，使知识和经验能够跨越项目周期与人员更替，长期积累和传承。
