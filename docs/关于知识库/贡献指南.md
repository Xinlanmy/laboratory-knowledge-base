# 总目录维护指南

部门章节正文在各部门自己的 GitHub 仓库维护。本仓库只登记目录与链接。

## 登记一个章节入口

1. 在章节所属部门仓库维护正文，并由该部门负责人审核。
2. 提供可直接阅读的章节 URL、所属分类、章节标题和一句话目录摘要。
3. 在本仓库的目录页和 `wiki/index.md` 登记这些信息；不要复制正文。
4. 在 `wiki/log.md` 追加本次目录调整记录。
5. 检查链接可访问、标题与实际章节一致，再提交 Pull Request。

## LLM Wiki 维护约定

- 部门仓库中的章节是正文来源；总目录提供导航，不替代章节。
- 助手可以提出页面改动，但来源、数字、版本、命令和实验结论必须由成员核实。
- 新来源可能修正旧结论时，注明变化、日期和依据，并检查依赖旧结论的页面。
- 有价值的问答总结可以沉淀成知识页，附来源与适用范围。
- 定期检查断链、孤立页、过时版本、来源缺失和冲突。

## 本地预览

```bash
python -m pip install -r requirements.txt
mkdocs serve
```

## 提交前检查

```bash
mkdocs build --strict
```

确认侧边栏可到达新文档，代码命令中的路径与版本已核对，图片和附件可访问。

链接分两类，检查方式不同：

- **站内链接**（相对路径、图片、锚点）：`mkdocs build --strict` 会直接报错。
- **外链**（`http(s)://…`）：由链接检查工作流负责，见 `.github/workflows/link-check.yml`。提 PR 时它会自动跑，发现的失效链接会让 PR 变红；每天 UTC 01:00 还会定时跑一次，定时失败自动记到 Issue 里（外面世界的链接会在我们没动代码的情况下失效）。

写示例链接时把示例放进行内代码——写成 `` `[标题](URL)` ``。链接检查同时会检查站内相对链接，裸写的占位符 `(URL)` 会被当成相对路径并报 `File not found`（这个坑在第一次跑链接门时就踩到了）。

登记新仓库或新章节时，请先按[登记与引用规范](登记与引用规范.md)的 §四、§五 检查字段与 URL 是否齐全、可达。
