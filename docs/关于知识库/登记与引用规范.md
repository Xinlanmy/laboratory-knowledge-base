# 实验室技术知识库登记与引用规范（v2）

> 本文件是主目录仓库**唯一权威**的结构与登记约定。v1《实验室技术知识库文档写入规范》中「正文该怎么写」的部分已归档到 [`docs/归档/`](../归档/实验室技术知识库文档写入规范-v1.md)，本仓库不再维护。
>
> 读这份文件的人：主目录维护者（登记与校验）、各部门负责人（需要提供什么）、AI 助手（改动的边界在哪）。

## 一、本仓库管什么，不管什么

| | 内容 |
|---|---|
| **管** | 目录结构、登记记录、链接可用性、来源关系、状态与变更留痕、跨仓库阅读导航 |
| **不管** | 章节正文的写法、正文的存放位置、成员个人评价 |

一条底线：**正文留在部门仓库，本仓库只登记，不复制**。在本仓库里出现大段正文，本身就是需要修的问题。

## 二、为什么这样定：四个场景

每条规则都能追溯到下面四类场景之一。判断一条规则该不该留，就看它服务哪个场景。

| 场景 | 谁在用 | 对应章节 |
|---|---|---|
| 想一步点到正文 | 任何成员 | §五 URL 规则 |
| 只想改自己部门那一行 | 部门负责人 | §七 单一来源 |
| 要能机器判定「链接还活着吗」 | 主目录维护者 | §四 固定字段、§十 三层校验 |
| 要结构化元数据才能检索 | 检索工具与 AI 助手 | §四 固定字段名 |

## 三、分类名由主书统一

全书固定六类，分类名不由各部门自定：

| 分类 | 回答的问题 |
|---|---|
| 基础知识 | 这个领域需要知道什么 |
| 技术模块 | 这个技术怎么理解和使用 |
| 学习课程 | 新成员按什么顺序学 |
| 项目实践 | 学完之后怎么真正做出来 |
| 技术经验 | 以前的人踩过什么坑 |
| 历史与交接 | 以前做过什么、现在到哪、下一步能做什么 |

部门仓库的内部目录名可以不同，用 §六 的对应表对齐。

## 四、登记记录

### 登记在哪

**唯一权威位置**是仓库根目录的 `sources/repositories.md`。分类页、Wiki 索引只做导航摘要并链接过去。

### 一条记录要有哪些字段

登记表 `sources/repositories.md` 当前的列与含义：

| 列 | 必填 | 说明 |
|---|---|---|
| 部门 | 是 | 用 §三 的分类体系里的部门名 |
| 部门/维护组 | 是 | 部门名 + GitHub 维护账号链接（`https://github.com/<账号>`） |
| 章节或路径 | 是 | 该仓库覆盖哪些分类、覆盖到什么程度，与 §六 对应表保持一致 |
| 正文仓库/页面 URL | 是 | 部门仓库或站点入口，按 §五 的 URL 规则书写 |
| 状态 | 是 | 见下方枚举 |

`最后核实` 这一字段保留在规范里，但登记表当前不设该列：`已登记` 的行用该部门分类入口小节的标题日期（如「终端服务部 · 分类入口（2026-10-12 起）」）与 `wiki/log.md` 的记录追溯最近一次实测；第三层校验上线时把它变成正式的一列。

### 状态枚举

| 状态 | 含义 |
|---|---|
| `待提供` | 知道有这个部门，但还没拿到仓库地址 |
| `待登记` | 拿到了地址，还没核实链接与分类 |
| `已登记` | 链接实测可用、分类已对齐 |
| `已失效` | 曾经可用，现在不可达；备注写明原因与日期 |

硬规则：

1. `已登记` ⇒ 维护账号、正文仓库 URL、可追溯的核实日期**同时存在**；
2. `已失效` ⇒ 必须写原因与日期，不要直接删行（删了就没人知道这里曾经有什么）；
3. 没有任何链接时只能写 `待登记` 或 `待提供`，**不得编造章节或仓库**。

## 五、URL 规则

1. **一步可达**：点开就是正文，不要指向还需要再点一次的中间页。
2. **优先目录级 URL**：登记「分类目录」而不是「某一篇文档」，部门在目录里增删文档不会让登记失效。
3. **提交前实测**：写进登记表的 URL，提交前打开一次。
4. **不登记还没上线的地址**：站点刚合并、Pages 还没部署完的页面，等部署完成再登记。
5. **站点与仓库都给**：面向读者的入口用站点 URL，面向维护者的入口用仓库 URL，两者都写不算重复。

## 六、分类名 ↔ 部门仓库目录对应表

主书分类名固定，部门目录名自定，两者靠对应表对齐。

对应表的**正本在 `sources/repositories.md`**：每个已登记部门一节「<部门> · 分类入口（起始日期）」，表头为「主书分类 | 部门仓库目录 | 入口」。本规范只规定格式与写法，不复制各行的具体映射，避免同一份映射两处维护；部门调整目录结构时改那一节，并同步各分类页的链接。

终端服务部那一节可作样例：

| 主书分类 | 部门仓库目录 | 说明 |
|---|---|---|
| 基础知识 | `参考/` | 概念与常识类内容 |
| 技术模块 | `参考/` | 一门技术一页 |
| 学习课程 | `学习/` | 有先后顺序的内容 |
| 项目实践 | `项目/` | 做出来的东西 |
| 技术经验 | `经验/` | 排障复盘 |
| 历史与交接 | `历史与交接/` | 进度与交接 |

两种特殊情况的写法：

- **目录与六类不是一一对应**（例如某部门按「学习、设计图、历史、项目、资料」五类组织）：一行可以填多个目录（如「`设计图/`、`资料/`」），但要在该节说明为什么这样归并。
- **某一类暂无对应目录**：填「暂无独立目录」，并写清内容现在落在哪个目录、待谁划分；**不得为凑满六类新建空目录**。

## 七、单一来源

同一个事实只写一处，别的地方链接过去。

- 部门仓库地址与状态：只写在 `sources/repositories.md`；
- 分类覆盖明细：写在 `sources/repositories.md` 的「章节或路径」列与对应表；分类页只写一句话现状与入口，Wiki 索引只写一句话摘要；
- 「终端服务部已登记」这类句子在多个页面重复出现，就是需要改的信号。

## 八、正文写作要求不由本仓库维护

- 章节正文的结构、质量标准、模板由**各部门自己的规范**决定，主书只链接过去；
- 本仓库 `docs/写作模板/` 下的模板是**可选起点**，不是对部门的要求；部门有自己的模板时以自己的为准；
- v1 的正文写作要求全文保留在 [`docs/归档/实验室技术知识库文档写入规范-v1.md`](../归档/实验室技术知识库文档写入规范-v1.md)，只作对照，不再更新。

## 九、变更流程

| 角色 | 该做什么 |
|---|---|
| 部门负责人 | 先在自己仓库改结构，再通知主书维护者更新 §六 对应表与分类页 |
| 主目录维护者 | 改 `sources/repositories.md` → 跑一次链接检查 → 在 `wiki/log.md` 追加记录 |
| AI 助手 | 可以提出并实施改动，但必须实测链接、不得编造章节或仓库；来源与状态由成员确认 |

## 十、可机器校验的三层

| 层 | 查什么 | 状态 |
|---|---|---|
| 第一层 · 链接门 | 所有 `*.md` 里的外链是否可达（lychee，PR 时跑 + 每天定时跑） | 已启用，见 `.github/workflows/link-check.yml` |
| 第二层 · 目录存在性 | 登记的仓库里是否真有这个目录（GitHub API 查 `contents/{path}`） | 计划中 |
| 第三层 · 字段完整性 | 登记表每行字段是否齐全、状态枚举是否合法 | 计划中 |

三层合起来能证明的是「链接活着、目录还在、字段填全了」。**证明不了**「链接指向的内容还是登记时那个东西」，那部分靠 §六 对应表加人工复核。

## 十一、留痕

每次收录、修订、修复链接，都在 `wiki/log.md` 追加一条，格式：

```text
## [YYYY-MM-DD] catalog | 标题
```

站点副本 `docs/wiki/log.md` 同步追加。历史条目不覆盖、不删除。

## 十二、和 v1 的差异

| | v1《文档写入规范》 | v2 本文件 |
|---|---|---|
| 定位 | 指导各部门怎么写正文 | 主书自己的登记与引用约定；正文写法归各部门 |
| 正本数量 | 同一份内容在仓库根目录、`docs/关于知识库/`、`docs/wiki/` 存了三份，已经开始漂移 | 只有本文件一份正本，其余位置是指向本文件的入口页 |
| 模板 | `templates/` 与 `docs/写作模板/` 两份，其中两份模板已不一致 | 正本只保留 `docs/写作模板/`，`templates/` 为入口页 |
| 链接检查 | 无 | 第一层已启用（PR + 每日定时，失败自动开 Issue） |
| 登记字段与状态 | 未规定 | §四 固定字段 + 状态枚举 + 硬规则 |
